## Goal

`query()` reaches full upstream filter parity: every filter
combination (`material=`, `labels=`, `states=`, `ips=`, multi-svar)
and the hidden `**kwargs` knobs (`subrec`, `source`,
`reference_state`, `face`, `output_object_labels`), with the typed
error hierarchy surfaced cleanly. The component-name derivation in
core catches up to the M3-deferred forms. The exit gate is the
upstream read-path test suite running against `milox` with only an
import redirect, plus a broad milox filter-combination parity table.

## The literal-README tension (resolved here — decision 16)

README § "Phase 2 milestones" M4: *"Run `reference/mili-python/tests/`
unmodified against the new module."* Taken literally over the whole
directory this is **not achievable at M4 and never was scoped to
be**:

- `test_append_states*.py`, `test_modify_database.py`, the write
  half of `test_afileIO.py`/`test_miliinternal.py` exercise the
  **write path** — explicitly `status.md` § "Deferred to Phase 3".
- The suite does `from mili import reader`,
  `from mili.milidatabase import MiliPythonError, ResultModifier`,
  `from mili.datatypes import Superclass, Metadata`,
  `from mili.mdg_defines import EntityType, ...`, and drives the
  full `MiliDatabase` wrapper (`__postprocess` + `reductions.combine`,
  `modifier`, `project_to_nodes`, `as_dataframe`, derived) via
  `reader.open_database(..., suppress_parallel=, merge_results=,
  procs=)`.

The README's own § "Public surface" / § "Non-goals" already resolves
the tension: *the post-processing wrappers stay in Python over the
Rust primal call for v1*. So "unmodified" means **the read-path test
modules run with only an import redirect onto a `mili`-API-compatible
`milox` package** — not a from-scratch Rust reimplementation of the
Python wrapper layer, and not the Phase-3 write modules.

**Decision 16 — port the upstream Python wrapper layer into `milox`,
thin over the Rust core.** `milox` gains, ported essentially verbatim
from `reference/mili-python/src/mili/`:

- `milox.reader.open_database(...)` — the `suppress_parallel` /
  `merge_results` / `procs` surface (today's `open_database` shim
  grows these kwargs).
- a `MiliDatabase`-equivalent wrapper: `__postprocess` +
  `reductions.combine`, `ResultModifier` (`__process_query_modifier`),
  `project_to_nodes` (`__project_result`), `as_dataframe`
  (`result_dictionary_to_dataframe`), the derived layer
  (`derived.py`), and the `EntityType`/`Superclass`/`Metadata`/
  `mdg_defines` enums the tests import.
- the per-database object underneath is the Rust-backed
  `PyMiliDatabase` (slots in where upstream's `_MiliInternal` sits;
  the `LoopWrapper`/`ServerWrapper` fan-out stays collapsed into the
  Rust `DatabaseSet` per m1.md decision-shape — the wrapper's public
  method-forwarding surface is what the tests touch and it is
  preserved).

This keeps the m1–m3 invariant intact: **parity-sensitive
ordering/string/value logic lives in the Rust core; everything
ported into the Python layer is non-parity post-processing already
written and tested upstream.** The write-back half of `write_data`,
`append_state`, `copy_non_state_data`, `modify_database` stay
Phase 3 — out of M4. The exit gate runs the read-path modules
(`test_milidatabase.py` read tests, `test_bugfixes.py`,
`test_miliinternal.py` read tests, `test_derived.py`,
`test_projection.py`, `test_reductions.py`, `test_grizinterface.py`,
`test_reader.py`, `test_adjacency.py`) — write modules xfail/skip
with a Phase-3 reason, not a silent pass.

## Slice A / Slice B split (RESOLVED during implementation)

The implementation surfaced a hard line between two bodies of work.
The user pre-authorized the contingency ("attempt in M4, split if it
balloons"); the evidence below splits it.

**Slice A — delivered in M4 (bit-exact cross-validated vs upstream
`mili`):**

- Core: `subrec=` filter plumbed through `Filter` /
  `collect_matching_subrecs` / `QueryArgs` (binding pass-through; new
  `query::tests::plan_subrec_filter_restricts_to_named_subrecord`).
- Core: `svar_query_meta` subscript form — `query("hx[3]")` →
  `["hx[3]"]`, `query("hx[8]")` → `["hx[8]"]`, bare `hx` → full
  `hx[1..=8]` (decision 17, subscript half). Proven bit-exact on
  `th/serial/d3samp6.th` vs upstream (components **and** data).
- Binding: `material=` (int / name / digit-string → numbers via the
  materials map), `labels=` (∩ `material` in core), `states=`
  (scalar / list / negative / `unique` / sorted), `ips=` (scalar /
  list / unique / sorted — pass-through; label semantics is Slice B),
  multi-svar (deduped, input order), `subrec=`, `**kwargs`
  validation → `MiliPythonError` (unexpected kw; `source!='primal'`,
  `reference_state`/`face`, `output_object_labels=False`,
  `write_data` all typed-errored with the Phase-3 / M4-followup
  reason). Verified vs upstream: vector / multi-state / negative /
  dedupe / `material` (1–4 on fdamp1) / `labels` / multi-svar /
  `subrec=1hex_mmsvn_rec` — all bit-exact (`test_query_parity.py`
  `test_filter_combination_parity`, 12 combos; + the Slice-A
  `test_bugfixes` value cases lifted verbatim).

**Slice B — split to M4-followup (recorded here, reason concrete):**
bare-component-of-**VEC_ARRAY** resolution (`sx`/`sy`/`syz`/`eps` on
`shell`/`brick`), the ip-as-**label** semantics (upstream `ips=` are
element-set IP *labels* matched via `__int_points`/`__element_sets`;
core `Filter.ips` is 0-based positional), the `f"{comp} ipt. {label}"`
component naming, and the cross-material `InconsistentIpCounts`
tightening (basic1 `sx`/`brick`, mat 5 = 8 IPs vs mat 7 = 9 IPs).
**Why split, not a `find_vector_parent` tweak:** the evidence shows
this needs (a) VEC_ARRAY-parent resolution *and* (b) a new
svar→element-set→IP-label linkage in core (the `__int_points`
recursive build has no `mili-rs` analogue) *and* (c) label→index
mapping *and* (d) cross-material per-subrec IP-count reconciliation —
four coupled core subsystems, well past the single extension the
decision-17 contingency scoped to M4. The exact upstream oracle
values (`test_bugfixes.py`) are encoded as
`xfail(strict=True)` cases (`test_bugfixes_slice_b_oracle`) so the
follow-up lands against a ready, self-tripping gate; the
cross-material **must-raise** contract is asserted today
(`test_bugfixes_cross_material_inconsistent_ips_contract`).

The full upstream-suite import-redirect + Python wrapper-layer port
(decision 16) is likewise M4-followup; M4 instead lifts the
cross-validatable `test_bugfixes` *values* directly into
`test_query_parity.py`, delivering that coverage without the port.

## M4-followup item 2 — wrapper-layer port: RE-SCOPED (decision 19)

> Decision 16 framed the upstream-suite import-redirect + Python
> wrapper-layer port as *"bulk, low-parity-risk … ~1900 test LOC"*.
> Implementation investigation (post-Slice-B) shows that framing is
> **wrong on both counts** and the item is re-scoped here.

**The facts (measured against the pinned submodules):**

- The upstream read-path suite drives **~50 `_MiliInternal` public
  methods** through the `MiliDatabase` wrapper.
  `crates/mili-py/src/database.rs` (`PyMiliDatabase`) exposes **13**.
  The ~37-method gap is not "post-processing already proven
  upstream" — it includes genuinely new, **parity-sensitive**
  computation with no `mili-rs` analogue: the `derived.py` engine
  (2440 LOC, value-producing), `adjacency.py` (313),
  `projection.py` (172, `project_to_nodes`), `faces`,
  `nodes_of_elems` / `nodes_of_material`, `geometric_mesh_info.py`.
- Read-path **test** LOC is **~7300** (not ~1900):
  `test_milidatabase.py` 2604, `test_miliinternal.py` 794,
  `test_derived.py` 1907, plus projection/reductions/adjacency/
  grizinterface/reader.
- Even the smallest module (`test_reader.py`, 68 LOC) needs the full
  `mili`-compatible **module/class skeleton** (`MiliDatabase`,
  `_MiliInternal`/`LoopWrapper`/`ServerWrapper` identities,
  `reader.open_database` kwargs, `afileIO.MiliFileNotFoundError`)
  before any redirect can collect.

Decision 16's invariant ("everything ported into Python is non-parity
post-processing") **does not hold** for `derived`/`projection`/
`adjacency`/`faces`: those compute values and must be parity-validated
like the primal path. They belong in the **Rust core** (m1–m3
precedent), not "verbatim Python over primal".
