## Goal

`query()` reaches full upstream filter parity: every filter
combination (`material=`, `labels=`, `states=`, `ips=`, multi-svar)
and the hidden `**kwargs` knobs (`subrec`, `source`,
`reference_state`, `face`, `output_object_labels`), with the typed
error hierarchy surfaced cleanly. The component-name derivation in
core catches up to the M3-deferred forms. The exit gate is the
upstream read-path test suite running against `milox` with only an
import redirect, plus a broad milox filter-combination parity table.

## The literal-README tension (resolved here — decision 16)

README § "Phase 2 milestones" M4: *"Run `reference/mili-python/tests/`
unmodified against the new module."* Taken literally over the whole
directory this is **not achievable at M4 and never was scoped to
be**:

- `test_append_states*.py`, `test_modify_database.py`, the write
  half of `test_afileIO.py`/`test_miliinternal.py` exercise the
  **write path** — explicitly `status.md` § "Deferred to Phase 3".
- The suite does `from mili import reader`,
  `from mili.milidatabase import MiliPythonError, ResultModifier`,
  `from mili.datatypes import Superclass, Metadata`,
  `from mili.mdg_defines import EntityType, ...`, and drives the
  full `MiliDatabase` wrapper (`__postprocess` + `reductions.combine`,
  `modifier`, `project_to_nodes`, `as_dataframe`, derived) via
  `reader.open_database(..., suppress_parallel=, merge_results=,
  procs=)`.

The README's own § "Public surface" / § "Non-goals" already resolves
the tension: *the post-processing wrappers stay in Python over the
Rust primal call for v1*. So "unmodified" means **the read-path test
modules run with only an import redirect onto a `mili`-API-compatible
`milox` package** — not a from-scratch Rust reimplementation of the
Python wrapper layer, and not the Phase-3 write modules.

**Decision 16 — port the upstream Python wrapper layer into `milox`,
thin over the Rust core.** `milox` gains, ported essentially verbatim
from `reference/mili-python/src/mili/`:

- `milox.reader.open_database(...)` — the `suppress_parallel` /
  `merge_results` / `procs` surface (today's `open_database` shim
  grows these kwargs).
- a `MiliDatabase`-equivalent wrapper: `__postprocess` +
  `reductions.combine`, `ResultModifier` (`__process_query_modifier`),
  `project_to_nodes` (`__project_result`), `as_dataframe`
  (`result_dictionary_to_dataframe`), the derived layer
  (`derived.py`), and the `EntityType`/`Superclass`/`Metadata`/
  `mdg_defines` enums the tests import.
- the per-database object underneath is the Rust-backed
  `PyMiliDatabase` (slots in where upstream's `_MiliInternal` sits;
  the `LoopWrapper`/`ServerWrapper` fan-out stays collapsed into the
  Rust `DatabaseSet` per m1.md decision-shape — the wrapper's public
  method-forwarding surface is what the tests touch and it is
  preserved).

This keeps the m1–m3 invariant intact: **parity-sensitive
ordering/string/value logic lives in the Rust core; everything
ported into the Python layer is non-parity post-processing already
written and tested upstream.** The write-back half of `write_data`,
`append_state`, `copy_non_state_data`, `modify_database` stay
Phase 3 — out of M4. The exit gate runs the read-path modules
(`test_milidatabase.py` read tests, `test_bugfixes.py`,
`test_miliinternal.py` read tests, `test_derived.py`,
`test_projection.py`, `test_reductions.py`, `test_grizinterface.py`,
`test_reader.py`, `test_adjacency.py`) — write modules xfail/skip
with a Phase-3 reason, not a silent pass.

## Slice A / Slice B split (RESOLVED during implementation)

The implementation surfaced a hard line between two bodies of work.
The user pre-authorized the contingency ("attempt in M4, split if it
balloons"); the evidence below splits it.

**Slice A — delivered in M4 (bit-exact cross-validated vs upstream
`mili`):**

- Core: `subrec=` filter plumbed through `Filter` /
  `collect_matching_subrecs` / `QueryArgs` (binding pass-through; new
  `query::tests::plan_subrec_filter_restricts_to_named_subrecord`).
- Core: `svar_query_meta` subscript form — `query("hx[3]")` →
  `["hx[3]"]`, `query("hx[8]")` → `["hx[8]"]`, bare `hx` → full
  `hx[1..=8]` (decision 17, subscript half). Proven bit-exact on
  `th/serial/d3samp6.th` vs upstream (components **and** data).
- Binding: `material=` (int / name / digit-string → numbers via the
  materials map), `labels=` (∩ `material` in core), `states=`
  (scalar / list / negative / `unique` / sorted), `ips=` (scalar /
  list / unique / sorted — pass-through; label semantics is Slice B),
  multi-svar (deduped, input order), `subrec=`, `**kwargs`
  validation → `MiliPythonError` (unexpected kw; `source!='primal'`,
  `reference_state`/`face`, `output_object_labels=False`,
  `write_data` all typed-errored with the Phase-3 / M4-followup
  reason). Verified vs upstream: vector / multi-state / negative /
  dedupe / `material` (1–4 on fdamp1) / `labels` / multi-svar /
  `subrec=1hex_mmsvn_rec` — all bit-exact (`test_query_parity.py`
  `test_filter_combination_parity`, 12 combos; + the Slice-A
  `test_bugfixes` value cases lifted verbatim).

**Slice B — split to M4-followup (recorded here, reason concrete):**
bare-component-of-**VEC_ARRAY** resolution (`sx`/`sy`/`syz`/`eps` on
`shell`/`brick`), the ip-as-**label** semantics (upstream `ips=` are
element-set IP *labels* matched via `__int_points`/`__element_sets`;
core `Filter.ips` is 0-based positional), the `f"{comp} ipt. {label}"`
component naming, and the cross-material `InconsistentIpCounts`
tightening (basic1 `sx`/`brick`, mat 5 = 8 IPs vs mat 7 = 9 IPs).
**Why split, not a `find_vector_parent` tweak:** the evidence shows
this needs (a) VEC_ARRAY-parent resolution *and* (b) a new
svar→element-set→IP-label linkage in core (the `__int_points`
recursive build has no `mili-rs` analogue) *and* (c) label→index
mapping *and* (d) cross-material per-subrec IP-count reconciliation —
four coupled core subsystems, well past the single extension the
decision-17 contingency scoped to M4. The exact upstream oracle
values (`test_bugfixes.py`) are encoded as
`xfail(strict=True)` cases (`test_bugfixes_slice_b_oracle`) so the
follow-up lands against a ready, self-tripping gate; the
cross-material **must-raise** contract is asserted today
(`test_bugfixes_cross_material_inconsistent_ips_contract`).

The full upstream-suite import-redirect + Python wrapper-layer port
(decision 16) is likewise M4-followup; M4 instead lifts the
cross-validatable `test_bugfixes` *values* directly into
`test_query_parity.py`, delivering that coverage without the port.

## M4-followup item 2 — wrapper-layer port: RE-SCOPED (decision 19)

> Decision 16 framed the upstream-suite import-redirect + Python
> wrapper-layer port as *"bulk, low-parity-risk … ~1900 test LOC"*.
> Implementation investigation (post-Slice-B) shows that framing is
> **wrong on both counts** and the item is re-scoped here.

**The facts (measured against the pinned submodules):**

- The upstream read-path suite drives **~50 `_MiliInternal` public
  methods** through the `MiliDatabase` wrapper.
  `crates/mili-py/src/database.rs` (`PyMiliDatabase`) exposes **13**.
  The ~37-method gap is not "post-processing already proven
  upstream" — it includes genuinely new, **parity-sensitive**
  computation with no `mili-rs` analogue: the `derived.py` engine
  (2440 LOC, value-producing), `adjacency.py` (313),
  `projection.py` (172, `project_to_nodes`), `faces`,
  `nodes_of_elems` / `nodes_of_material`, `geometric_mesh_info.py`.
- Read-path **test** LOC is **~7300** (not ~1900):
  `test_milidatabase.py` 2604, `test_miliinternal.py` 794,
  `test_derived.py` 1907, plus projection/reductions/adjacency/
  grizinterface/reader.
- Even the smallest module (`test_reader.py`, 68 LOC) needs the full
  `mili`-compatible **module/class skeleton** (`MiliDatabase`,
  `_MiliInternal`/`LoopWrapper`/`ServerWrapper` identities,
  `reader.open_database` kwargs, `afileIO.MiliFileNotFoundError`)
  before any redirect can collect.

Decision 16's invariant ("everything ported into Python is non-parity
post-processing") **does not hold** for `derived`/`projection`/
`adjacency`/`faces`: those compute values and must be parity-validated
like the primal path. They belong in the **Rust core** (m1–m3
precedent), not "verbatim Python over primal".

### Feasibility (the blocker is policy, not data)

The per-fragment data is **fully retained in Rust** —
`mili_rs::DatabaseSet` owns `fragments: Vec<Database>` and already
exposes `fragment_count()` / `fragment(rank)` / `fragments()`. So this
is **not** a core data-model change; it is an *additive* FFI + Python
wrapper-layer slice. What blocks it today is a deliberate **policy**:
`DatabaseSet`'s public accessors *merge* across fragments (per
`reductions.py` semantics, m1.md decision-shape), and decision 19
pinned "the `LoopWrapper`/`ServerWrapper` fan-out stays collapsed into
the Rust `DatabaseSet`". The redirect harness encodes that policy by
xfailing every parallel-handler class as "Rust DatabaseSet collapses
the per-proc fan-out".

### What the parallel suite actually needs

`GrizInterface.__init__` and the `LoopWrapper*`/`ServerWrapper*` test
classes drive the upstream **`merge_results=False`** contract: every
public accessor returns a **per-proc list** (`db._mili.parameters()` →

shape unconditionally and `reductions.combine` is identity.

not a reversal)

### Decision 22 — the on-disk A/T/S writer lives in the Rust core (amends nothing; applies decision 19 to the write direction)

The Rust core (`crates/mili-rs`) was READ-ONLY (mmap over A/T/S, no
writer). Phase 3 adds the write direction. The central question:
where does the byte-layout writer live — (a) the Rust core, with its
own `parity_write*.rs` gate diffing milox-written bytes vs
upstream-`mili`-written bytes on the same corpus, or (b) a verbatim
Python port of upstream `afileIO.AFileParser`+`AFileWriter` into
milox (the decision-18/21 verbatim-plumbing precedent)?

**Decision: (a) — the writer lives in the Rust core
(`mili_rs::write`), gated by `crates/mili-rs/tests/parity_write_append.rs`.**

Rationale (decision 19 applied to the write direction): writing the
on-disk A/T/S format **is** parity-sensitive byte layout
(`planning/shared/format.md` / `entry-payloads.md`). Decision 19's
invariant is "parity-sensitive value/topology + byte-layout
computation in the Rust core; non-parity plumbing verbatim in
Python". The renormalising A-file serializer (directory re-ordering
into upstream's `dir_order`, the rebuilt string pool, the
recomputed offsets/lengths/dir-decls, the rebuilt `STATE_VAR_DICT`
int/char stream, the smap + footer) is exactly that byte-layout
surface — it gets its own `parity_*.rs` gate, not a Python
re-implementation of layout.

**Trade-off recorded.** Option (b) (verbatim-port `afileIO` into
`milox`) would be bit-exact *by construction* (it would literally be
upstream's code) and lower-effort — the decision-21 precedent. It
was rejected because it **also requires porting upstream's
`AFileParser`** (a second, parallel A-file parser independent of the
Rust core that already parses every A-file structure), duplicating
the core's single-source-of-truth parsing responsibility and
contradicting decision 19's "byte layout in the core, parity-gated"
invariant. Option (a) keeps one parser/model and a real bit-exact
write gate; the cost is re-deriving upstream's exact serialization in
Rust. That cost is **bounded by an empirical finding** (logged in
`status.md` § Surprises): for the d3samp6 corpus upstream's
`AFileWriter` emits **byte-identical payloads to the original `.A`
mmap ranges for every non-`STATE_VAR_DICT` directory** (42/42
params/class-def/class-idents/nodes/elem-conns + `SREC_DATA`), so the
core writer copies those payload byte-ranges verbatim and rebuilds
**only** `STATE_VAR_DICT` (upstream renormalises its int/char stream)
+ the string pool + dir-decls + smap + footer + the 16-byte header
(also a verbatim original-range copy). milox Python stays thin
plumbing: `_MiliInternal.append_state`/`copy_non_state_data` auto-
forward to the new `PyMiliDatabase` FFI via the existing
`__getattr__`; `MiliDatabase._REDUCE_FUNCTIONS` already maps both to
`reductions.zeroth_entry`; the `LoopWrapper`/`ServerWrapper` per-proc
fan-out is the decision-21 verbatim mechanism (each fragment's
`open_single` core does its own write).

### Decision 23 — `query(write_data=)` is a Rust-core scatter that inverts the read `ReadPlan` (extends decision 22; applies decision 19 to the write-half)

Phase 3.2's central question: how does the `write_data` `QueryDict`
reach the on-disk state bytes — (a) re-derive upstream's
`srec.calculate_memory_offsets` / `extract_ordinals` scatter as a
separate write algorithm, or (b) **invert the read gather** the core
already builds?

**Decision: (b) — `Database::scatter_query` builds the *same*
per-state `ReadPlan` a read of `(svar, class, labels, states, ips,
subrec)` would, then writes the `write_data` values into exactly
those byte slabs (`rb+`, each state at its smap data-start).** It is
the byte-for-byte inverse of `run_query`'s gather and the
generalisation of Phase 3.1's single-svar `scatter_state_field`
primitive to an arbitrary svar / class / label-set / state-set /
ip-set from a `QueryDict`. The `write_data`-label → result-order
realignment upstream spells `argsort`/`searchsorted`
(`miliinternal.py:1331-1334`) is reproduced by mapping the plan's
result labels back into the `write_data['layout']['labels']` order;
the state axis is positional (upstream indexes `write_data['data']`
by the requested-state position `sidx`, not a state-label lookup).

Rationale (decision 19/22 invariant): the scatter **is**
parity-sensitive byte layout — the precise inverse of the gate-locked
read planner — so it lives in the core, not as a second Python offset
algorithm. Reusing the read plan means one offset-derivation, one
source of truth, gated bit-exact by
`crates/mili-rs/tests/parity_write_query.rs` (oracle
`query(write_data=)` vs core scatter, state bytes diffed on
serial/sstate + a parallel fragment). Corollary recorded as a
surprise (`status.md`): `append_state` must **atomically** rewrite
its own live-mmapped `.A` (write-then-rename) and refresh the
in-memory model — upstream `_MiliInternal.append_state` mutates its
`__smaps` so the same object re-queries the new state, and is itself
implemented *in terms of* `query(write_data=)` for the nodpos/sand
patch (`miliinternal.py:1518-1538`); milox's engine is the core, so
it reloads the just-rewritten `.A` (already byte-exact, Phase 3.1).
The Phase-3.1-flagged "serial-sstate multi-entry-per-sname directory
merge" turned out **not to arise** — empirically that corpus has no
duplicate snames and the serializer was already bit-exact on it; the
real append-to-existing blocker was the stale in-memory model
(logged under `status.md` § Surprises).

### Decision 24 — `AppendStatesTool` is a verbatim Python port (applies decision 18/19; the inverse of decisions 22/23)

Phase 3.3's central question: does the input-dictionary batch tool
(`mili.append_states.AppendStatesTool`, 366 lines) need Rust-core work,
or is it a verbatim Python port like `reductions` / `utils` /
`projection` / `adjacency` (decision 18/19 precedent)?

**Decision: (b) — verbatim Python port into `milox.append_states`,
only the `mili.*` imports repointed at `milox`.** `AppendStatesTool`
contains **no byte-layout computation**: it is input-spec validation
(`VALID_OUTPUT_TYPES`/`VALID_OUTPUT_MODES`, `states`/`state_times`/
`time_inc`, `limit_*`, the per-svar shape/jagged/int-point checks) plus
orchestration that *drives* the already-bit-exact write primitives —
`copy_non_state_data` + `append_state` (Phase 3.1, decision 22,
`parity_write_append.rs`) and `query(write_data=)` (Phase 3.2,
decision 23, `parity_write_query.rs`) over the parity-correct read
accessors. This is the exact inverse of decisions 22/23: *there* the
question was a byte-layout writer (→ Rust core, own `parity_*.rs`
gate); *here* there is no new numerical/layout kernel, so running the
*same* Python validation+reshape over bit-exact primitives reproduces
upstream by construction. Behaviourally gated by the redirected
`test_append_states_tool.py` (23 cases); byte-gated by the new
`crates/mili-rs/tests/parity_write_append_states_tool.rs` (upstream
`mili` tool vs `milox` tool, `.A` + state files byte-diffed on
serial/sstate, `append` + `write` modes).

**Three milox completeness gaps the port surfaced** (logged in
`status.md` § Surprises), all read-path bugs latent until the tool
exercised them:

1. `_MiliInternal.state_variables()` returned flat `StateVariable`s
   with `svars=[]` unpopulated, so `atom_qty` summed an empty list →
   `0` for every VECTOR/VEC_ARRAY. Added upstream's recursive
   `svars[]` population (`miliinternal.py:140-146`).
2. A directly-queried element-set VEC_ARRAY (`query("es_3c","shell",
   ips=[2])`) interpreted `ips=` as a 0-based positional index, not
   the integration-point *label* upstream uses (`.index(ip)` against
   the element-set payload, `miliinternal.py:191,1251-1270`) — wrong
   IP silently selected, or a spurious `IpOutOfRange`. `resolve_atom_picker`
   now label-maps `ips` for an element-set self-entry, matching the
   bare-component substitution path.
3. A state-less `copy_non_state_data` output (no `<root>T` tfile,
   smaps written inline by `AFileWriter` with `allow_tfile=False`)
   failed to reopen ("directory expects tfile…"). The family layer
   now treats a missing tfile as a valid 0-state inline map, mirroring
   upstream `afileIO`'s tfile-only-if-on-disk read.

### Decision 25 — redirect-coverage closeout: the exclusion boundary (applies decision 18/19/22; closes Phase 3 against drift)

Phase-3 closeout audited **every** `reference/mili-python/tests/
test_*.py` against the harness `_REDIRECTED` list. 11 were already
redirected-and-promoted; 5 were not. The scope question: for each
un-redirected file, is it a read-path/parity surface that must be
wired-and-promoted (Phase-3.x protocol), or a non-API surface to
*consciously exclude*?

**Decision: 2 redirect-and-promote, 3 explicit-exclude.**

- **`test_utils` → redirected, fully promoted (20 cases).** Pure
  result-reshape helpers over the parity-correct `QueryDict` (decision
  18/19, like `reductions`/`projection`). The only gap was the last
  missing verbatim port — `dataframe_to_result_dictionary` — added to
  `milox.utils` (inverse of the already-ported
  `result_dictionary_to_dataframe`; no new kernel).
- **`test_bugfixes` → redirected, fully promoted (17 cases).**
  Read-path regression queries over the dir_version_2 / basic1 /
  vrt_BS / fdamp1 / beam_udi / d3samp4 / labeling / vecarray / th
  corpora — squarely parity surface. Surfaced one real milox metadata
  gap: `Subrecord.state_byte_offset` was never populated (sentinel
  `-1`). Now derived in the Rust core
  (`mili_rs::reshape::subrecords`, cumulative `object_count *
  bytes_per_object` over the flattened srec list — upstream
  `miliinternal.py:271-272`), exposed via the `subrecords()` FFI tuple.
  Same class of latent read-path completeness fix as decision 24's
  three.
- **`test_imports` / `test_afileIO` / `test_plotting` → `EXCLUDED`
  (commented, in the harness).** None is a parity/read-path API
  assertion: `test_imports` is a no-corpus import-smoke test that
  imports `mili.plotting` (the matplotlib presentation layer milox does
  not port — decision 18/19 scope); `test_afileIO` exercises upstream's
  internal *pure-Python* afileIO parser/writer object model, which
  decision 22 explicitly relocates to the Rust core (no Python
  re-implementation to redirect onto — its byte fidelity is gated by
  `parity_write_*.rs`); `test_plotting` is matplotlib/PIL image-baseline
  rendering of query results (presentation, not parity; the queries it
  plots are covered by the redirected read-path modules). These are
  documented non-gaps, like the `*_alt` griz listing-only variants.

**The gate that makes it un-regressible.** A new
`test_redirect_coverage_is_exhaustive` asserts `{every test_*.py} ==
set(_REDIRECTED) ∪ EXCLUDED` (skip-not-fail if the submodule is
absent), and a strict 0-xfail `pytest_sessionfinish` in
`crates/mili-py/tests/conftest.py` fails the session on any
xfail/xpass. Both run in CI's `test-milox` job, so a future submodule
bump that adds an unredirected `test_*.py`, or any silently-diverging
case, is a hard CI failure — the only remaining silent-rot path (empty
xfail bucket) is closed.
