# `mili-py` M1 — scaffolding + metadata accessors

> Scope doc for Phase 2 Milestone 1. Builds on
> [`README.md`](README.md) (overall design, crate shape, exception
> hierarchy) and the **pinned FFI contract** in
> [`../mili-rs/plan.md`](../mili-rs/plan.md) § "FFI integration plan
> (Phase 1.5 — Step 19)". Read [`../mili-rs/status.md`](../mili-rs/status.md)
> § "Known gaps Phase 2 inherits" and § "Resolved: deferred
> query-merge parity gap" first — M1's `DatabaseSet` binding depends
> on the latter.

## Goal

Stand up the PyO3 module and the Python-side test harness, and bind
the read-only **metadata** surface (no bulk data arrays yet — those
are M2). Exit criterion: `open_database()` returns a Rust-backed
object whose metadata accessors are bit-exact against upstream
`mili-python` on the parity corpus, single- *and* multi-fragment.

## In scope for M1

- **Crate scaffold.** `crates/mili-py/` per README § "Crate shape"
  (workspace crate stays `mili-py`; PyPI dist + import package are
  both `milox`): `crate-type = ["cdylib"]`,
  `#[pymodule] milox._native`, `pyo3` + `numpy` (rust-numpy),
  `maturin` / `pyproject.toml` (`[project] name = "milox"`,
  `tool.maturin.module-name = "milox._native"`).
  Workspace-gated so the existing `cargo test --workspace` stays
  binding-free (binding crate behind a workspace member that the
  default test job doesn't compile, or its own CI job).
- **`open_database()` Python shim.** Filename-root parsing /
  suffix-stripping stays in Python (README § "Filename root parsing")
  — the Rust core takes a resolved path. The shim counts fragments
  and constructs the right backing object (see binding shape below).
- **`PyMiliDatabase`** wrapping either `mili_rs::Database` or
  `mili_rs::DatabaseSet`, chosen at open time by fragment count.
- **Metadata accessors only:** `times()`, `state_count()`,
  `class_names()`, `labels()`, `state_maps()`, `materials()`,
  `material_numbers()`, `element_sets()`, `integration_points()`,
  `mesh_dimensions()`. (`nodes()`, `connectivity()`, `query()` are
  M2/M3.)
- **Error mapping.** `errors.rs`: `MiliError` → the three-class
  Python hierarchy (README § "Exception hierarchy"), including the
  Phase-1.5 additions `NoFragments` / `FragmentMismatch` and the
  Phase-2-inherited `InconsistentIpCounts` — surfaced as
  `MiliPythonError` subclasses with the typed detail preserved in
  the message.
- **Parity harness.** pytest that imports the Rust-backed module and
  diffs metadata accessors against upstream `mili` on every parity
  corpus fixture + the xmilics multi-fragment families.

## Out of scope for M1 (deferred to later milestones)

- Any bulk array return (`nodes`, `connectivity`, `query`) — M2/M3.
- `as_dataframe`, `modifier`, `write_data`, `project_to_nodes`,
  derived results — stay in Python on top of the Rust primal call;
  M4+.
- The `Arc<Mmap>`/`PyCapsule` zero-decode path — pinned to M5.

## Pinned FFI contract M1 binds against

From `../mili-rs/plan.md` § "FFI integration plan":

- **GIL.** Every call that runs a `mili-rs` rayon section wraps the
  Rust call in `pyo3::Python::allow_threads`. M1's metadata
  accessors are cheap and mostly non-parallel, but `query()` (M3)
  and the `DatabaseSet::open` fan-out **do** run rayon, so the
  pattern is established now: accessors that can block release the
  GIL.
- **Zero-FFI-copy return.** `IntoPyArray::into_pyarray_bound(py)` on
  an owned `Vec<T>` / `ndarray::Array<T,_>` is the **default** return
  path (numpy adopts the heap buffer, no byte copy). `ToPyArray` only
  when ownership can't transfer. M1 returns mostly small Python
  lists/ints so this bites at M2; pin the helper signatures now.
- **`DatabaseSet` binding shape.** `PyMiliDatabase` is a thin wrapper
  over `Database` *or* `DatabaseSet` selected at open time by
  fragment count. The upstream `LoopWrapper` / `ServerWrapper` are
  **not** ported — their fan-out/merge job lives in
  `DatabaseSet`. The Python-side `Mili` factory still exists but
  returns the Rust-backed object.

## Dependency on the Task-2 fix (now resolved)

`DatabaseSet`'s merged accessors are only trustworthy because of the
PR-#13 follow-up: `query_with_labels` now emits real entity labels
(was MO ordinals) and the merge replicates
`merge_result_dictionaries` exactly (see
`../mili-rs/status.md` § "Resolved: deferred query-merge parity
gap"). M1's multi-fragment metadata parity (`labels()` especially)
and M3's `query()` parity both **rest on that fix**. It is landed and
bit-exact-parity-covered (`parity_d3samp6_set_query_nodpos`), so M1
can proceed.

## Resolved decisions (settled before coding)

1. **Zero-copy default — RESOLVED.** The pinned FFI contract
   (`../mili-rs/plan.md` § "FFI integration plan") is authoritative:
   `IntoPyArray::into_pyarray_bound` ownership-transfer is the
   default array return; `ToPyArray` only when ownership can't
   transfer; the `Arc<Mmap>`/`PyCapsule` borrow path is deferred to
   M5 (profiling-driven). The README § "Zero-copy plan" has been
   annotated "superseded by plan.md § FFI" so the doc drift is gone.
   Not blocking M1 (no array returns until M2) but settled now.
2. **`QueryDict` shape — RESOLVED.** `PyMiliDatabase.query` returns
   a plain constructed Python `dict`
   (`{svar: {data, layout:{labels,states,times,components}, source,
   title, class_name, modifier}}`), **not** a `#[pyclass]` mapping —
   drop-in compatibility with downstream code that indexes the dict
   beats a typed wrapper. The `tests/parity_support` decoder already
   assumes this shape. Locked at M3; recorded here so M1's harness
   scaffolding builds toward it.
3. **Workspace gating — RESOLVED.** `mili-py` gets a **dedicated CI
   job** mirroring `test-parity`'s Python/maturin setup, and is
   **excluded from the default workspace test set** so the fast
   `test` job (`cargo test --workspace`) never links pyo3. Mechanism:
   keep `mili-py` a workspace member for unified `cargo` ergonomics
   but add `--exclude mili-py` (or an explicit member list) to the
   default `test` job; the new job runs `maturin develop` + pytest.
   No feature-flag indirection.
4. **`state_maps()` across fragments — RESOLVED.** Upstream's
   parallel reduction is `zeroth_entry` (`milidatabase.py:194`) —
   i.e. rank-0's view — which is exactly what
   `DatabaseSet::state_maps()` already returns. Decision: bind it
   straight through and **add a parity assertion in the M1 harness**
   locking `state_maps()` equality vs. upstream on a multi-fragment
   xmilics family, so any future reduction drift is caught.

## Still open (non-blocking, revisit at the named milestone)

- **Returned-array writability** (README § "Open questions"). numpy
  arrays from `IntoPyArray` are writable by default; current
  mili-python `np.frombuffer` results are read-only. Decide at M2
  whether to freeze (`.setflags(write=False)`) for behavioral parity
  — needs a check that no upstream test mutates a returned array.
- **Derived results dtype/shape assumptions** — verify at M4 when
  the Python derived layer first runs on Rust primal arrays.
