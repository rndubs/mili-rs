## Goal

Bind `nodes()` and `connectivity()` on `PyMiliDatabase` — the first
bulk arrays across the FFI boundary — bit-exact (dtype, shape, values)
against upstream `mili` on the parity corpus, single- *and*
multi-fragment. Establish the owned-`Vec` → `into_pyarray_bound`
zero-FFI-copy 2-D return path and pin the array-helper signatures so
M3's `query()` reuses them.

## In scope for M2

- **`PyMiliDatabase.nodes()`** → `np.float32` array shaped
  `(n_nodes, mesh_dim)`. Matches upstream
  `miliinternal.py:341` / `milidatabase.py:167`.
- **`PyMiliDatabase.connectivity(class_name=None)`** → element
  **LABELS** form (`miliinternal.py:608`): `np.int32` array shaped
  `(n_elem, nodes_per_elem + 1)` (node columns label-substituted,
  trailing column = raw material number, part column dropped). With
  `class_name=None`, a `{class_name: array}` dict over element classes
  only (upstream `__conns_labels` keys = ELEM_CONNS snames).
- **Zero-FFI-copy 2-D return path.** Owned `Vec<T>` from core →
  `into_pyarray_bound(py)` → `.reshape((rows, cols))`, the Rust call
  under `allow_threads`. Helper signatures pinned for M3 reuse.
- **Harness extension.** `crates/mili-py/tests/test_arrays_parity.py`
  diffs `nodes()` / `connectivity()` (dtype, shape, values) vs
  upstream over `conftest.CASES` (serial + xmilics multi-fragment).

## Out of scope (later milestones)

- `connectivity_ids()` (raw fortran-indexed form) — not in the M2
  surface; add when a real call needs it.
- `query()` — M3.
- `Arc<Mmap>`/`PyCapsule` zero-decode — M5.

## Pinned FFI contract M2 binds against

Unchanged from m1.md. The load-bearing primitives M2 first exercises:

- **Default zero-FFI-copy return.** Owned `Vec<T>` /
  `ndarray::Array<T,_>` → `IntoPyArray::into_pyarray_bound(py)`; numpy
  adopts the heap buffer. 2-D shape via `.reshape((rows, cols))` on the
  bound array (a view, no copy). `ToPyArray` is *not* used — core
  hands the binding owned `Vec`s in both the `Database` and
  `DatabaseSet` arms (resolves the API asymmetry: the binding never
  returns a borrowed `Nodes<'_>`/`Connectivity<'_>` view).
- **GIL.** The core decode/merge runs inside `py.allow_threads`.

## Resolved decisions (settled before coding)

9. **`connectivity()` label-substitution lives in `mili-rs` core —
   RESOLVED.** Upstream `connectivity()` returns the
   label-substituted, part-dropped, material-kept form
   (`miliinternal.py:217-223`); `mili-rs`'s `Connectivity::to_i32_vec`
   is the raw on-disk stream (fortran node ids + material + part). Per
   the M1 precedent (core owns array/metadata parity; the binding is a
   thin pass-through), the substitution belongs in core. New
   `Database::connectivity_labels` / `DatabaseSet::connectivity_labels`
   return owned `(Vec<i32>, ncols)`. The raw borrowed
   `connectivity()` / `to_i32_vec()` primitives are unchanged (still
   used by `mesh_fixtures`, `family_set` internals).

10. **`nodes()` cross-fragment merge is dedup-by-label, NOT plain
    concat — RESOLVED (core parity fix).** Upstream
    `milidatabase.py:167-185` for the multi-fragment / merged case is
    *not* a registered reduce — it concatenates per-fragment node
    labels, takes `np.unique(..., return_index=True)`, `indexes.sort()`,
    and selects those coordinate rows (first occurrence of each unique
    node label, in rank-concat order). The pre-M2
    `DatabaseSet::nodes` was plain concat — a multi-fragment parity
    bug. Fixed in `DatabaseSet::node_coords`. Single-fragment
    `Database::node_coords` concatenates **all** NODES entries
    (upstream iterates `NODES.items()`), not just the first.

11. **`connectivity()` cross-fragment merge is `list_concatenate` of
    the per-fragment LABEL form — RESOLVED.**
    `reductions.reduce_connectivity` = `list_concatenate` (row concat,
    axis 0, no remap, no dedup) over each fragment's
    `_mili.connectivity()` — which is already the label-substituted
    form. `DatabaseSet::connectivity_labels` substitutes per fragment
    (using *that fragment's* own node labels) then row-concats. The
    pre-M2 `DatabaseSet::connectivity` concatenated the *raw* stream —
    wrong shape and values vs upstream `MiliDatabase.connectivity()`.

12. **Returned-array writability — RESOLVED: leave writable, no
    `.setflags(write=False)`.** The m1.md "Still open" freeze question
    assumed upstream arrays are read-only `np.frombuffer` views. They
    are not for these two accessors: upstream `nodes()` returns a
    `np.concatenate` result and `connectivity()` returns a `.copy()` —
    **both writable**. No upstream test mutates a returned
    `nodes()`/`connectivity()` array in place (only slicing/compare).
    `IntoPyArray` arrays are writable, which matches. The
    `np.frombuffer` read-only concern is real but `query()`-specific
    (state data); the freeze decision is re-flagged for **M3** where it
    actually applies.

## Core parity fixes M2 lands (the appropriate place)

Same precedent as M1's corpus-driven fixes — `mili-rs` core owns
array parity; the binding stays a thin pass-through.

- `Database::node_coords(mesh) -> Result<Option<(Vec<f32>, usize)>>`
  — concat all NODES entries; `usize` = mesh dimensions.
- `Database::connectivity_labels(mesh, class) -> Result<Option<(Vec<i32>, usize)>>`
  — label-substituted (`node_labels[id-1]`), part dropped, material
  kept; `usize` = columns = `conn_words - 1`. Iterates all
  `conns_entry_indices`.
- `DatabaseSet::node_coords` — dedup-by-label merge (decision 10).
- `DatabaseSet::connectivity_labels` — per-fragment label form,
  row-concat (decision 11).

`status.md` § "Surprises worth remembering" gets entries for the
label-substituted-`connectivity()` distinction and the
dedup-by-label `nodes()` merge.
